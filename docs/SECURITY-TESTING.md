## 1. ทำไมระบบนี้ต้องทดสอบความปลอดภัย

ระบบพี่เงินเก็บ**ข้อมูลการเงินส่วนบุคคล** ได้แก่ รายรับ-รายจ่ายรายวัน ยอดเงินคงเหลือ
เป้าหมายการออม สลิปโอนเงินที่ผู้ใช้อัปโหลด และบทสนทนาที่ผู้ใช้เล่าเรื่องการเงินให้ AI ฟัง

ข้อมูลกลุ่มนี้อ่อนไหวกว่าข้อมูลทั่วไป เพราะเปิดเผยพฤติกรรมและฐานะทางการเงินของบุคคล
ความเสี่ยงที่ร้ายแรงที่สุดจึงไม่ใช่ "เว็บล่ม" แต่คือ **ผู้ใช้คนหนึ่งเห็นข้อมูลของอีกคน**

เอกสารนี้จึงออกแบบการทดสอบโดยให้น้ำหนักกับเรื่องนั้นเป็นหลัก

## 2. ขอบเขตการทดสอบ

### สิ่งที่ทดสอบ

- REST API ทั้งหมดภายใต้ `/api/v1/*` (การเงิน งบประมาณ เป้าหมาย แชท การแจ้งเตือน พยากรณ์)
- กลไกยืนยันตัวตนด้วย JWT
- การตรวจสอบข้อมูลขาเข้า (input validation)
- HTTP security headers
- การจำกัดอัตราการเรียกใช้ (rate limiting)

### สิ่งที่ไม่ได้ทดสอบ (และเหตุผล)

| ไม่ได้ทดสอบ | เหตุผล |
|---|---|
| การโจมตีระดับโครงสร้างพื้นฐาน (DDoS จริง) | อยู่นอกความรับผิดชอบ — Render/Cloudflare ดูแลชั้นนี้ |
| ความปลอดภัยของ Neon (ฐานข้อมูล) | เป็นบริการภายนอกที่มีมาตรฐานของตัวเอง |
| การเจาะระบบผู้ให้บริการ AI (Typhoon/Groq/OpenAI) | เป็นบริการภายนอก |
| Social engineering | ไม่ใช่ช่องโหว่เชิงเทคนิคของระบบ |

## 3. วิธีการทดสอบ

ใช้แนวทาง **Black-box testing** คือทดสอบจากภายนอกโดยไม่เรียกฟังก์ชันภายในโปรแกรม
ยิงคำขอ HTTP เข้าไปที่เซิร์ฟเวอร์จริงเหมือนผู้โจมตีที่มีแค่ URL ของเว็บ

### สถานการณ์จำลอง

สคริปต์จะสร้างผู้ใช้ทดสอบ 2 คนบนระบบจริง:

| ผู้ใช้ | บทบาท |
|---|---|
| **ผู้ใช้ ก** | ผู้โจมตี — พยายามเข้าถึงข้อมูลของคนอื่น |
| **ผู้ใช้ ข** | เหยื่อ — มีรายจ่าย ฿250, เป้าหมายออม ฿50,000 และห้องแชทเป็นของตัวเอง |

จากนั้นให้ **ก** พยายามอ่าน แก้ไข และลบข้อมูลของ **ข** ด้วยวิธีต่าง ๆ
เมื่อทดสอบเสร็จ สคริปต์จะลบบัญชีทดสอบทั้งสองทิ้งอัตโนมัติ ไม่ทิ้งขยะไว้ในฐานข้อมูล

> **หมายเหตุด้านจริยธรรม:** ทดสอบเฉพาะระบบที่คณะผู้จัดทำเป็นเจ้าของ
> ใช้บัญชีที่สร้างขึ้นเองเท่านั้น ไม่แตะต้องข้อมูลของผู้ใช้จริงแม้แต่รายการเดียว
> อีเมลทดสอบใช้โดเมน `.invalid` ตาม RFC 2606 ซึ่งส่งอีเมลจริงไม่ได้

### วิธีรัน

```bash
cd backend
npm run test:security              # ทดสอบ production
npm run test:security -- --local   # ทดสอบเครื่องตัวเอง
```

## 5. ช่องโหว่ที่ตรวจพบและการแก้ไข

**การรันครั้งแรกได้ผล 27/33 ไม่ใช่ 33/33** — พบช่องโหว่จริง 6 รายการ ซึ่งได้แก้ไขครบแล้ว
หัวข้อนี้เป็นหลักฐานว่าการทดสอบมีประโยชน์จริง ไม่ได้เขียนขึ้นเพื่อให้ผ่านเพียงอย่างเดียว

### 5.1 ไม่มีการจำกัดอัตราการเรียกใช้ — ระดับ สูง

**ปัญหา** ระบบเดิมไม่จำกัดจำนวนครั้งที่เรียก API ได้เลย ส่งผลให้

1. เดารหัสผ่านแบบอัตโนมัติได้ไม่จำกัดจำนวนครั้ง
2. เรียก `/api/v1/chat` รัว ๆ ได้ ซึ่งทุกครั้งจะเรียกโมเดลภาษาที่**คิดค่าบริการตามการใช้งานจริง**
   ผู้ไม่หวังดีจึงทำให้เจ้าของระบบเสียค่าใช้จ่ายได้
3. ระบบรับข้อมูลได้ถึง 15MB ต่อคำขอ (สำหรับรูปสลิป) การยิงซ้ำ ๆ ทำให้เซิร์ฟเวอร์ล่มได้ง่าย

**การแก้ไข** เพิ่มการจำกัดอัตราแบบแยกตามความเสี่ยงของแต่ละกลุ่ม

| กลุ่ม | เพดาน | เหตุผล |
|---|---|---|
| สมัคร/ล็อกอิน | 10 ครั้ง / 5 นาที | พอสำหรับคนพิมพ์ผิดบ้าง แต่ตัดการเดารหัสอัตโนมัติ |
| แชท AI | 30 ครั้ง / นาที | เกินความเร็วที่คนพิมพ์ไหว แต่กันสคริปต์ยิงรัว |
| ทุก endpoint | 300 ครั้ง / นาที | เผื่อไว้มาก เพราะหน้าแดชบอร์ดเรียกหลาย API พร้อมกัน |

**บทเรียนที่ได้** ตอนแรกออกแบบผิด 2 จุดและตรวจพบก่อนนำขึ้นใช้งานจริง

1. ลืมตั้งค่า `trust proxy` — เซิร์ฟเวอร์อยู่หลัง reverse proxy ของ Render
   ถ้าไม่ตั้ง ระบบจะมองว่าผู้ใช้ทุกคนมาจากเลข IP เดียวกัน (ของ proxy)
   แล้วนับรวมกันทั้งหมด ผลคือ**ผู้ใช้จริงจะถูกบล็อกยกแผง**
2. นำการจำกัดอัตราที่ใช้กันเดารหัสผ่านไปครอบทุก endpoint ในกลุ่ม `/auth`
   ทำให้การลบบัญชีตัวเองถูกบล็อกไปด้วยทั้งที่ไม่เกี่ยวกัน
   แก้เป็นใส่เฉพาะ endpoint ที่รับรหัสผ่านจริง

### 5.2 ส่งจำนวนเงินเกินขอบเขตทำให้เซิร์ฟเวอร์ตอบ 500 — ระดับ ปานกลาง

**ปัญหา** ส่ง `amount: 1e308` แล้วเซิร์ฟเวอร์ตอบ **500 Internal Server Error**
เพราะคอลัมน์เก็บเงินเป็นชนิด Int ของ PostgreSQL ซึ่งรับได้สูงสุด 2,147,483,647
เมื่อค่าเกินขอบเขต ฐานข้อมูลจึงโยนข้อผิดพลาดออกมา

การตอบ 500 ทั้งที่เป็นความผิดของข้อมูลขาเข้าเป็นปัญหา 2 ชั้น
ชั้นแรกคือผู้ใช้ไม่รู้ว่าตนส่งอะไรผิด ชั้นที่สองคือเปิดโอกาสให้ยิงคำขอแบบนี้ซ้ำ ๆ
เพื่อสร้างภาระให้ระบบ

**การแก้ไข** กำหนดเพดานที่ชั้นตรวจสอบข้อมูล `MAX_SATANG = 2,000,000,000`
(เท่ากับ 20 ล้านบาท) กับทุก schema ที่รับจำนวนเงิน ระบบจึงปฏิเสธด้วย **400** ตั้งแต่ต้นทาง

### 5.3 ไม่มี HTTP Security Headers และเปิดเผยเทคโนโลยีที่ใช้ — ระดับ ปานกลาง

**ปัญหา** ไม่มี header ป้องกันมาตรฐาน และส่ง `X-Powered-By: Express` ซึ่งบอกผู้โจมตี
ว่าควรไปค้นหาช่องโหว่ของเทคโนโลยีตัวไหน

**การแก้ไข** เพิ่ม `helmet` และปิดการส่ง `X-Powered-By`

### 5.4 กุญแจลับมีค่าสำรองอยู่ในซอร์สโค้ดสาธารณะ — ระดับ สูง (เชิงป้องกัน)

**ปัญหา** โค้ดเดิมกำหนดว่าถ้าไม่พบการตั้งค่า `JWT_SECRET` ให้ใช้ค่าสำรองที่เขียนไว้ในไฟล์
เนื่องจากซอร์สโค้ดเปิดเป็นสาธารณะ ทุกคนจึงอ่านค่านี้ได้

การทดสอบยืนยันว่า**ระบบที่ใช้งานจริงตั้งค่ากุญแจลับไว้ถูกต้องแล้ว** (ข้อ 2.2 ผ่าน)
แต่โครงสร้างแบบนี้เป็นความเสี่ยงแฝง เพราะหากวันใดการตั้งค่าหายไป ระบบจะไม่แจ้งเตือนใด ๆ
เพียงแต่เปลี่ยนไปใช้กุญแจสาธารณะเงียบ ๆ แล้วใครก็ปลอมตัวเป็นผู้ใช้คนใดก็ได้

**การแก้ไข** เปลี่ยนเป็นให้เซิร์ฟเวอร์ **ปฏิเสธการเริ่มทำงาน** ทันทีถ้าไม่พบกุญแจลับในโหมด production
ตามหลัก *fail fast* คือหยุดทำงานอย่างชัดเจนดีกว่าทำงานต่อในสภาพที่ไม่ปลอดภัย

### 5.5 เพิ่มสิทธิขอลบข้อมูลตาม พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล

เพิ่ม `DELETE /api/v1/auth/me` ให้ผู้ใช้ลบบัญชีและข้อมูลทั้งหมดของตนเองได้
ข้อมูลที่เกี่ยวข้องทั้งหมด (รายการเงิน งบประมาณ เป้าหมาย แชท การแจ้งเตือน)
จะถูกลบตามโดยอัตโนมัติผ่านการตั้งค่า cascade ในฐานข้อมูล

## 8. แผนการนำเสนอ (10–12 นาที)

### ลำดับการนำเสนอ

| ช่วง | เวลา | เนื้อหา |
|---|---|---|
| 1 | 1 นาที | **ตั้งประเด็น** — ระบบเก็บข้อมูลการเงินส่วนบุคคล ความเสี่ยงร้ายแรงที่สุดไม่ใช่เว็บล่ม แต่คือผู้ใช้คนหนึ่งเห็นข้อมูลของอีกคน |
| 2 | 2 นาที | **วิธีทดสอบ** — อธิบายสถานการณ์ผู้ใช้ ก กับ ผู้ใช้ ข และเน้นว่าทดสอบจากภายนอกบนระบบจริง ไม่ใช่เรียกฟังก์ชันภายใน |
| 3 | 3 นาที | **สาธิตสด** — รัน `npm run test:security` ให้เห็นผลไล่ทีละข้อ |
| 4 | 4 นาที | **ช่องโหว่ที่เจอและวิธีแก้** — จุดที่ควรใช้เวลามากที่สุด |
| 5 | 2 นาที | **ข้อจำกัดและงานต่อไป** — แสดงว่าเข้าใจว่าอะไรยังไม่ครอบคลุม |

### จุดที่ควรเน้น

**ห้ามนำเสนอว่า "ผ่าน 33/33 จบ"** เพราะฟังดูเหมือนเขียนเทสให้ผ่านเอง
สิ่งที่ควรเน้นคือ **"รันครั้งแรกได้ 27/33 แล้วเจอช่องโหว่จริง 6 ข้อ"**
เพราะพิสูจน์ว่าการทดสอบมีคุณค่าจริง

ประเด็นที่น่าสนใจที่สุดสำหรับผู้ฟังคือ **การจำกัดอัตราการเรียกใช้ AI**
เพราะเป็นความเสี่ยงที่ระบบทั่วไปไม่มี — ระบบเราเรียกโมเดลภาษาที่คิดเงินตามการใช้งาน
ถ้าถูกยิงรัว ๆ เจ้าของระบบจะเสียเงินจริง ไม่ใช่แค่เซิร์ฟเวอร์ทำงานหนัก

### คำถามที่อาจารย์น่าจะถาม และแนวทางตอบ

**ถาม: ทำไมตอบ 404 ไม่ตอบ 403**
ตอบ: เพราะ 403 เท่ากับยืนยันว่าข้อมูลชิ้นนั้นมีอยู่จริงแต่ไม่ใช่ของผู้ขอ
ซึ่งเป็นการรั่วข้อมูลอย่างหนึ่ง การตอบ 404 ทำให้ผู้โจมตีแยกไม่ออกว่า
ข้อมูลไม่มีอยู่จริง หรือมีอยู่แต่ไม่ใช่ของตน

**ถาม: ทดสอบบน production เสี่ยงไหม**
ตอบ: ใช้บัญชีที่สคริปต์สร้างขึ้นเองทั้งหมด อีเมลใช้โดเมน `.invalid` ซึ่งส่งอีเมลจริงไม่ได้
ทดสอบเสร็จลบทิ้งอัตโนมัติ ไม่แตะข้อมูลผู้ใช้จริงแม้แต่รายการเดียว
และการทดสอบบนระบบจริงให้ผลที่เชื่อถือได้มากกว่าเพราะครอบคลุมการตั้งค่าจริงของเซิร์ฟเวอร์ด้วย

**ถาม: ทำไมเก็บเงินเป็นสตางค์**
ตอบ: เลขทศนิยมในคอมพิวเตอร์เก็บค่าไม่ตรงเป๊ะ เช่น 0.1 + 0.2 ไม่เท่ากับ 0.3 พอดี
เมื่อคำนวณสะสมหลายครั้งจะคลาดเคลื่อน ซึ่งยอมรับไม่ได้ในระบบการเงิน
จึงเก็บเป็นจำนวนเต็มหน่วยสตางค์แทน แล้วหารด้วย 100 ตอนแสดงผล

**ถาม: ครอบคลุมแล้วหรือยัง**
ตอบ: ครอบคลุมความเสี่ยงหลักตาม OWASP Top 10 ที่เกี่ยวข้องกับระบบนี้
แต่ยังมีข้อจำกัดตามหัวข้อที่ 7 เช่นการเพิกถอน token ก่อนหมดอายุ
และการย้ายตัวนับ rate limit ไป Redis เมื่อขยายเป็นหลายเซิร์ฟเวอร์

### เตรียมตัวก่อนสาธิต

- ทดลองรันล่วงหน้า 1 รอบให้แน่ใจว่าเซิร์ฟเวอร์ตื่นอยู่ (Render พักเซิร์ฟเวอร์เมื่อไม่มีคนใช้)
- **เว้นระยะอย่างน้อย 5 นาทีก่อนรันซ้ำ** ไม่งั้นจะติดการจำกัดอัตราของระบบตัวเอง
  หากเกิดขึ้นระหว่างสาธิต ให้ใช้เป็นข้อดี — เพราะเป็นการพิสูจน์สด ๆ ว่าหมวดที่ 8 ทำงานจริง
- ขยายขนาดตัวอักษรใน Terminal ให้ผู้ฟังแถวหลังอ่านออก

## 1. ทำไมระบบการเงินต้องทดสอบความน่าเชื่อถือ

ระบบที่ปลอดภัยแต่คำนวณผิด ก็ใช้งานไม่ได้อยู่ดี

สำหรับผู้ช่วยการเงิน ความเสียหายจาก "ตัวเลขผิด" ร้ายแรงเป็นพิเศษ เพราะผู้ใช้จะ
**ตัดสินใจเรื่องเงินจริงบนข้อมูลที่ผิด** เช่น เชื่อว่าตัวเองเหลือเงินมากกว่าความจริง
หรือเชื่อว่าระบบตั้งเป้าหมายออมให้แล้วทั้งที่ไม่มีเป้าหมายนั้นอยู่จริง

ระบบนี้มีจุดที่ข้อมูลอาจคลาดเคลื่อนได้ 4 จุดใหญ่ ซึ่งเอกสารนี้ทดสอบครบทั้งหมด

| จุดเสี่ยง | ความเสียหายถ้าผิด |
|---|---|
| การคำนวณเงิน | ยอดเงินเพี้ยนสะสมโดยไม่มีใครสังเกต |
| การอ่านสลิปโอนเงิน | บันทึกยอดผิด หรือหยิบค่าธรรมเนียมมาแทนยอดจริง |
| การตีความคำสั่งผู้ใช้ | "อยากเก็บเงิน 30,000" ถูกบันทึกเป็นรายจ่าย 30,000 |
| คำตอบของ AI | กุตัวเลขขึ้นมาเอง หรืออ้างว่าทำงานให้แล้วทั้งที่ไม่ได้ทำ |

## 2. วิธีการทดสอบ

หลักการเดียวกันทุกหมวด: **ป้อนข้อมูลที่รู้คำตอบล่วงหน้า แล้วเทียบผลลัพธ์กับคำตอบจริง**

| ประเภท | หมวด | ทำงานอย่างไร |
|---|---|---|
| ทดสอบในเครื่อง | 1, 2, 3 | เรียกฟังก์ชันตรง ๆ ไม่ต้องต่อเน็ต ผลคงที่ทุกครั้ง |
| ทดสอบผ่าน API จริง | 4, 5, 6 | สร้างบัญชีทดสอบบน production ป้อนข้อมูล แล้วอ่านผลกลับมาเทียบ |

บัญชีทดสอบใช้อีเมลโดเมน `.invalid` (RFC 2606 — ส่งอีเมลจริงไม่ได้) และถูกลบทิ้ง
อัตโนมัติเมื่อจบการทดสอบ ไม่แตะข้อมูลผู้ใช้จริงแม้แต่รายการเดียว

### วิธีรัน

```bash
cd backend
npm run test:reliability              # ทดสอบ production
npm run test:reliability -- --local   # ทดสอบเครื่องตัวเอง
npm run test:reliability -- --no-ai   # ข้ามหมวดที่เรียก AI (เร็ว/ไม่เปลืองโควต้า)
```

## 5. บั๊กที่ชุดทดสอบนี้ตรวจพบ

การรันครั้งแรกได้ 31/32 ไม่ใช่ผ่านหมด หัวข้อนี้บันทึกสิ่งที่พบและวิธีแก้

### 5.1 AI บอกว่า "ตั้งเป้าหมายให้แล้ว" ทั้งที่ไม่ได้สร้าง — ระดับ สูง

**อาการ** ผู้ใช้ขอให้ตั้งเป้าหมายออม AI ตอบว่า *"พี่เงินช่วยตั้งไว้ในระบบเรียบร้อยแล้ว"*
พร้อมอธิบายแผนการออมอย่างละเอียด แต่ในระบบไม่มีเป้าหมายนั้นอยู่จริง

นี่คือความเสียหายที่ตรงกับเหตุผลที่ต้องมีเอกสารนี้ — ผู้ใช้เชื่อว่างานถูกทำให้แล้ว
แล้ววางแผนการเงินต่อบนความเชื่อนั้น

| สมมติฐาน | ผลการตรวจ |
|---|---|
| ไม่มี tool ให้เรียก | ❌ มี `create_goal` พร้อมคำอธิบายครบ |
| คำสั่ง (prompt) ไม่ชัดเจน | ❌ ระบุชัดเจน รวมถึงห้ามไว้ว่า "ห้ามบอกว่าสร้างให้แล้วถ้ายังไม่ได้เรียกเครื่องมือ" |
| ถูกตัวตรวจจับอื่นดักไปก่อน | ❌ `detectQuickLog` และ `detectExportRequest` ไม่เข้าเงื่อนไข |
| ไม่ได้เปิดโหมดเครื่องมือ | ❌ `includeFinancialContext` เป็น true จึงเข้าเส้นทางที่มีเครื่องมือ |
| **โมเดลไม่เรียกเครื่องมือเอง** | ✅ **ใช่** — ทดสอบ 3 สำนวน ไม่เรียกเลยสักครั้ง |

**การแก้ไข** ใช้แนวทางเดียวกับที่โค้ดนี้เคยแก้ปัญหาเดียวกันกับการจดรายรับ-รายจ่าย
คอมเมนต์เดิมในโค้ดเขียนไว้เองว่า *"ไม่ต้องพึ่ง LLM เรียก tool ซึ่งบางโมเดลไม่นิ่ง"*

เพิ่ม `detectGoalIntent` ตรวจเจตนาผู้ใช้ด้วยกฎที่กำหนดไว้แน่นอน แล้วสร้างเป้าหมาย
ในโค้ดโดยตรง การกระทำจึงเกิดขึ้นแน่นอน ไม่ขึ้นกับว่าโมเดลจะเรียกเครื่องมือหรือไม่
พร้อมกันนั้นยังคง tool `create_goal` ไว้สำหรับสำนวนที่ตัวตรวจจับจับไม่ได้

**บทเรียน** เมื่อความถูกต้องของการกระทำสำคัญ อย่าฝากไว้กับการตัดสินใจของโมเดลภาษา
ให้เขียนกฎที่ตรวจสอบได้ไว้ในโค้ด แล้วใช้โมเดลภาษาทำสิ่งที่มันถนัดคือเรียบเรียงคำตอบ

### 5.2 ชื่อร้านมีวงเล็บว่างค้าง — ระดับ ต่ำ

**อาการ** สลิปที่มีเลขผู้เสียภาษีในวงเล็บ เช่น `ร้านกาแฟดี (1234567890123)`
ระบบตัดเลขออกถูกต้องแต่ทิ้งวงเล็บไว้ ได้ชื่อเป็น `"ร้านกาแฟดี ()"`

**การแก้ไข** ลบวงเล็บที่เหลือว่างและเครื่องหมายวรรคตอนท้ายชื่อออกหลังตัดตัวเลข

### 5.3 ข้อผิดพลาดในชุดทดสอบเอง — บันทึกไว้เป็นบทเรียน

ระหว่างพัฒนา พบว่าสคริปต์อ่านคำตอบของ AI จากฟิลด์ผิด (`body.text` แทน
`body.message.content`) แต่เทสยัง **"ผ่าน"** เพราะโค้ดตกไปที่การแปลงข้อมูลทั้งก้อน
เป็นข้อความ แล้วบังเอิญเจอตัวเลขที่ต้องการอยู่ข้างใน

**บทเรียน: เทสที่ผ่านไม่ได้แปลว่าเทสถูกต้อง** ต้องตรวจสอบด้วยว่ามันวัดสิ่งที่ตั้งใจวัดจริง
วิธีที่ใช้คือเขียนสคริปต์แยกพิมพ์ข้อมูลดิบออกมาดูด้วยตาก่อนเชื่อผลลัพธ์

### 5.4 เกณฑ์วัดที่ตั้งผิดจุด — บันทึกไว้เป็นบทเรียน

เดิมข้อ 5.3 บังคับให้ AI ต้องพูดคำว่า "ไม่มี" เมื่อถูกถามถึงข้อมูลที่ไม่มีในระบบ
แต่รอบหนึ่ง AI เลี่ยงไปตอบยอดรวมแทน ซึ่ง**ไม่ใช่การกุข้อมูล** แต่เทสตัดว่าผิด

เปลี่ยนไปวัดสิ่งที่ต้องการวัดจริง คือ "มีการอ้างตัวเลขที่ไม่มีอยู่จริงหรือไม่"
ไม่ใช่ "เลือกใช้ถ้อยคำแบบไหน" — เกณฑ์ใหม่ยังจับการกุตัวเลขได้เหมือนเดิม

## 6. ข้อจำกัดและข้อเสนอแนะในอนาคต

### 6.1 ข้อทดสอบที่ผลแกว่งได้ (ข้อ 5.2)

ระบบเรียกผู้ให้บริการโมเดลภาษาภายนอกตามลำดับ Typhoon → Groq → OpenAI
ถ้าทุกรายล้มเหลว ระบบจะใช้ **"คำตอบสำรอง"** ที่เขียนไว้ล่วงหน้าแทน

จากการทดสอบพบว่าสถานะนี้เกิดขึ้นเป็นครั้งคราวจริงบน production
ข้อ 5.2 จึงถูกเพิ่มเข้ามาเพื่อให้มองเห็นสถานะนี้ได้ชัดเจน เพราะโหมดคำตอบสำรอง
อันตรายกว่าที่คิด — ผู้ใช้จะได้คำตอบกว้าง ๆ ที่ดูเหมือนใช้ได้แต่ไม่อิงข้อมูลจริง
และเรียกใช้เครื่องมือใด ๆ ไม่ได้

**ข้อเสนอแนะ** แจ้งผู้ใช้ให้ทราบเมื่ออยู่ในโหมดคำตอบสำรอง แทนที่จะตอบเหมือนปกติ

### 6.2 ข้อจำกัดอื่น

| หัวข้อ | สถานะปัจจุบัน | ข้อเสนอแนะ |
|---|---|---|
| ชุดทดสอบสลิป | ใช้ข้อความ OCR ตัวอย่าง 10 รูปแบบที่มาจากบั๊กจริง | เก็บสลิปจริง 50 ใบจากหลายธนาคารมาทำชุดทดสอบมาตรฐาน จะได้ตัวเลขความแม่นยำที่อ้างอิงได้กว้างขึ้น |
| การพยากรณ์ (Prophet) | ยังไม่ได้วัดความแม่นยำ | ทำ backtesting — เทรนด้วยข้อมูล 6 เดือนแรก ทำนายเดือนที่ 7 แล้ววัดค่าความคลาดเคลื่อน (MAPE) |
| ความแม่นยำการจัดหมวดหมู่ | ยังไม่ได้วัด | สร้างชุดข้อมูลที่เฉลยหมวดไว้ แล้ววัดอัตราการจัดถูก |
| การทดสอบภาระงานหนัก | ยังไม่ได้ทำ | ทดสอบผู้ใช้พร้อมกันจำนวนมาก และผู้ใช้ที่มีรายการหลักหมื่น |
| การรันอัตโนมัติ | รันด้วยคำสั่งเอง | ผูกเข้ากับ GitHub Actions ให้รันทุกครั้งที่ส่งโค้ด |

## 7. แผนการนำเสนอ (เสริมจากเอกสารความปลอดภัย)

หากนำเสนอต่อจากหัวข้อความปลอดภัย ให้เชื่อมด้วยประโยคว่า
**"ระบบที่ปลอดภัยแต่คำนวณผิด ก็ใช้งานไม่ได้อยู่ดี"**

### จุดที่ควรเน้น 3 อย่าง

**1. ข้อ 1.1 — เห็นภาพที่สุดและอธิบายง่ายที่สุด**
โชว์ตัวเลขสองบรรทัดเทียบกัน: `1,000.00` กับ `1,000.0000000001588`
แล้วอธิบายว่าทำไมระบบการเงินจึงห้ามเก็บเงินเป็นทศนิยม

**2. หมวดที่ 3 — แสดงว่าเข้าใจว่า "ไม่ทำ" ก็สำคัญเท่ากับ "ทำ"**
7 ใน 12 ข้อเป็นการทดสอบว่าระบบต้อง **ไม่** ทำงาน เช่น "จ่ายค่าโน้ตบุ๊ค 30000"
ต้องไม่กลายเป็นเป้าหมายออม ซึ่งต่างจาก "อยากเก็บเงินซื้อโน้ตบุ๊ค 30000" แค่คำเดียว

**3. หัวข้อ 5.1 — บั๊กที่เล่าได้ดีที่สุด**
AI พูดว่าทำงานให้แล้วทั้งที่ไม่ได้ทำ · เล่าตั้งแต่วิธีตรวจพบ ไปจนถึงการตัดสมมติฐาน
ทีละข้อจนเจอสาเหตุ และบทสรุปว่า **"เมื่อความถูกต้องสำคัญ อย่าฝากไว้กับการตัดสินใจ
ของโมเดลภาษา"** — ประเด็นนี้เป็นข้อคิดเชิงวิศวกรรมที่ใช้ได้กับงาน AI ทุกประเภท

### คำถามที่อาจารย์น่าจะถาม

**ถาม: วัดความแม่นยำการอ่านสลิปจากสลิปจริงกี่ใบ**
ตอบ: ชุดทดสอบปัจจุบันใช้ข้อความ OCR ตัวอย่าง 10 รูปแบบ ซึ่งทุกรูปแบบมาจาก
บั๊กจริงที่ผู้ใช้แจ้งเข้ามา จึงครอบคลุมกรณีที่เคยพลาดจริงครบถ้วน
แต่ยอมรับว่ายังไม่ใช่ชุดข้อมูลขนาดใหญ่ — ระบุไว้เป็นข้อจำกัดในหัวข้อ 6.2

**ถาม: ถ้า AI ตอบไม่เหมือนเดิมทุกครั้ง จะทดสอบได้อย่างไร**
ตอบ: ไม่ทดสอบว่า "ตอบด้วยถ้อยคำอะไร" แต่ทดสอบว่า "ตัวเลขที่อ้างตรงกับฐานข้อมูลไหม"
และ "การกระทำที่บอกว่าทำแล้วเกิดขึ้นจริงไหม" ซึ่งตรวจสอบได้แน่นอนแม้คำตอบจะต่างกัน
บทเรียนข้อนี้อยู่ในหัวข้อ 5.4 ซึ่งเคยตั้งเกณฑ์ผิดมาก่อนแล้วแก้

**ถาม: ทำไมต้องมีตัวตรวจจับด้วยกฎ ในเมื่อมี AI แล้ว**
ตอบ: เพราะทดสอบแล้วพบว่าโมเดลไม่เรียกเครื่องมือที่จำเป็น การกระทำที่มีผลต่อข้อมูล
ผู้ใช้จึงไม่ควรขึ้นกับการตัดสินใจของโมเดล ระบบใช้ทั้งสองอย่างร่วมกัน — กฎรับประกัน
ว่าการกระทำเกิดขึ้นแน่นอน ส่วน AI ทำหน้าที่เรียบเรียงคำตอบให้เป็นธรรมชาติ

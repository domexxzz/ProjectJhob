# คู่มือตอบคำถามเชิงลึก — การทดสอบความปลอดภัยและความน่าเชื่อถือ

เอกสารนี้เตรียมไว้สำหรับการสอบปากเปล่า ใช้คู่กับ
[เอกสารทดสอบความปลอดภัย](SECURITY-TESTING.md) และ [เอกสารทดสอบความน่าเชื่อถือ](RELIABILITY-TESTING.md)

สองฉบับนั้นมีคำถามพื้นฐานอยู่แล้ว ฉบับนี้เน้น **คำถามที่จี้จุดอ่อน**
ซึ่งเป็นคำถามที่กรรมการมักถามเพื่อดูว่าผู้ทำเข้าใจงานตัวเองจริงหรือแค่ทำตามสูตร

---

## หลักการตอบ 3 ข้อ

**1. ยอมรับข้อจำกัดก่อนถูกจับได้**
กรรมการรู้อยู่แล้วว่าโครงงานนักศึกษามีข้อจำกัด สิ่งที่เขาวัดคือ
"รู้ตัวไหมว่าข้อจำกัดอยู่ตรงไหน" การตอบว่า *"ข้อนี้ยังไม่ได้ทำ เพราะ... ถ้าจะทำต้อง..."*
ได้คะแนนมากกว่าการเลี่ยงหรือกลบเกลื่อน

**2. ตอบด้วยตัวเลขและหลักฐาน ไม่ตอบด้วยความรู้สึก**
มี: ผลรัน 33 ข้อ / 45 ข้อ, บั๊กจริงที่เจอ, บันทึกการส่งอีเมลจากผู้ให้บริการ
ห้ามตอบว่า "น่าจะปลอดภัย" หรือ "คิดว่าแม่น"

**3. แยกให้ออกระหว่าง "ไม่ได้ทดสอบ" กับ "ทดสอบแล้วไม่ผ่าน"**
สองอย่างนี้ต่างกันมาก ต้องรู้ว่าอะไรคืออะไรในงานตัวเอง

---

## หมวด A — คำถามเรื่องความน่าเชื่อถือของการทดสอบเอง

### A1. "ทดสอบเองแล้วบอกว่าผ่านเอง จะเชื่อได้ยังไง"

คำถามนี้ถามบ่อยที่สุดและตรงที่สุด

**ตอบ:** ชุดทดสอบนี้ไม่ได้ออกแบบให้ผ่าน — **รันครั้งแรกได้ 27/33 และ 31/32**
พบช่องโหว่จริง 6 รายการและบั๊กจริง 2 รายการ ทั้งหมดบันทึกไว้ในเอกสารพร้อมวิธีแก้
ถ้าเขียนเพื่อให้ผ่านคงไม่มีหัวข้อ "บั๊กที่ตรวจพบ" ยาวขนาดนั้น

เสริมได้อีกว่า **มีข้อทดสอบที่ยังไม่ผ่านและไม่ได้ปิดทิ้ง** คือข้อที่ตรวจว่า AI
ตอบด้วยโมเดลจริงหรือคำตอบสำรอง ซึ่งผลแกว่งตามผู้ให้บริการภายนอก

### A2. "ทำไมไม่ใช้เครื่องมือมาตรฐาน เช่น OWASP ZAP หรือ Burp Suite"

**ตอบ:** เครื่องมือสแกนอัตโนมัติเก่งเรื่องช่องโหว่ที่มีรูปแบบตายตัว
(SQL injection, XSS, security headers) แต่**จับ Broken Access Control ไม่ได้**
เพราะมันไม่รู้ว่า "ข้อมูลชิ้นนี้ควรเป็นของใคร"

ซึ่งความเสี่ยงอันดับหนึ่งของระบบการเงินคือข้อนั้นพอดี จึงต้องเขียนเองโดยจำลอง
ผู้ใช้ 2 คนแล้วให้คนหนึ่งพยายามเข้าถึงข้อมูลอีกคน — เครื่องมือสำเร็จรูปทำแทนไม่ได้

**ยอมรับ:** ยังไม่ได้รันเครื่องมือสแกนอัตโนมัติเสริม ถ้ามีเวลาควรรัน ZAP เพิ่ม
เพื่อครอบคลุมช่องโหว่รูปแบบตายตัวที่เราอาจนึกไม่ถึง

### A3. "Test coverage กี่เปอร์เซ็นต์"

**ระวัง — อย่าตอบมั่ว** เราไม่ได้วัด code coverage

**ตอบ:** ไม่ได้วัดเป็น code coverage เพราะชุดทดสอบนี้เป็นแบบ black-box
ยิงผ่าน HTTP จากภายนอก ไม่ได้เรียกฟังก์ชันภายในโดยตรง จึงวัดเป็น
**behavior coverage** แทน คือครอบคลุม endpoint หลักทั้งหมดและความเสี่ยงตาม OWASP
ที่เกี่ยวข้องกับระบบนี้

**ยอมรับ:** ถ้าต้องการตัวเลข coverage ต้องเพิ่ม unit test แยกอีกชุด ซึ่งยังไม่ได้ทำ

### A4. "ทดสอบบน production ไม่เสี่ยงเหรอ ทำไมไม่ทำบน staging"

**ตอบ:** เสี่ยงถ้าออกแบบไม่ดี จึงวางกติกาไว้ 3 ข้อ
บัญชีทดสอบสร้างเองทั้งหมด · อีเมลใช้โดเมน `.invalid` ตาม RFC 2606 ซึ่งส่งจริงไม่ได้ ·
ลบทิ้งอัตโนมัติเมื่อจบ ไม่แตะข้อมูลผู้ใช้จริงแม้แต่รายการเดียว

ข้อดีคือได้ทดสอบ**การตั้งค่าจริงของเซิร์ฟเวอร์**ด้วย ซึ่ง staging จับไม่ได้ —
ตัวอย่างจริงคือกรณีที่พบว่าโฮสต์บล็อกพอร์ตส่งอีเมล ถ้าทดสอบแต่ในเครื่องจะไม่มีวันเจอ

**ยอมรับ:** ถ้าเป็นระบบที่มีผู้ใช้จริงจำนวนมาก ควรมี staging แยก

## หมวด B — คำถามเจาะเทคนิค

### B1. "JWT เก็บไว้ที่ไหนบนเครื่องผู้ใช้ ปลอดภัยไหม"

คำถามนี้แหลม เพราะคำตอบมีจุดอ่อนจริง

**ตอบตามจริง:**

| แพลตฟอร์ม | เก็บที่ | ระดับความปลอดภัย |
|---|---|---|
| มือถือ | `flutter_secure_storage` (Keychain/Keystore) | ดี — ระบบปฏิบัติการเข้ารหัสให้ |
| เว็บ | `localStorage` | อ่อนกว่า — สคริปต์ในหน้าเว็บอ่านได้ |

**เหตุผลที่ต้องใช้ localStorage บนเว็บ:** `flutter_secure_storage` บนเว็บต้องใช้
`crypto.subtle` ซึ่งมีเฉพาะบน HTTPS ตอนทดสอบผ่าน IP ภายในจะพัง

**สิ่งที่ลดความเสี่ยง:** หน้าเว็บเป็น Flutter ที่วาดลงผืนผ้าใบ (canvas)
ไม่ได้เอาข้อความจากผู้ใช้ไปสร้าง HTML จึงไม่มีช่องให้ฝังสคริปต์แบบเว็บทั่วไป
และมี header `X-Content-Type-Options` กับ `X-Frame-Options` ป้องกันเพิ่ม

**ยอมรับ:** ถ้าจะให้ปลอดภัยที่สุดควรใช้ httpOnly cookie ซึ่งสคริปต์อ่านไม่ได้เลย
แต่ต้องเปลี่ยนวิธียืนยันตัวตนทั้งระบบและเพิ่มการป้องกัน CSRF

### B2. "token อายุ 7 วัน ถ้าโทรศัพท์หายจะทำยังไง เพิกถอนได้ไหม"

**ตอบ:** **เพิกถอนไม่ได้** — เป็นข้อจำกัดที่ระบุไว้ในเอกสารแล้ว
JWT เป็นแบบ stateless เซิร์ฟเวอร์ไม่ได้เก็บรายการ token ที่ออกไป จึงยกเลิกกลางคันไม่ได้

**สิ่งที่ทำได้ตอนนี้:** เปลี่ยนรหัสผ่านผ่านระบบ OTP ซึ่งจะทำให้รหัส OTP
ที่ค้างอยู่ใช้ไม่ได้ทั้งหมด แต่ token เดิมยังใช้ได้จนหมดอายุ

**ทางแก้ที่ควรทำถ้าขยายผลจริง:** เพิ่มระบบ refresh token คู่กับ access token
อายุสั้น (15 นาที) แล้วเก็บรายการ refresh token ไว้ในฐานข้อมูลเพื่อให้เพิกถอนได้

### B3. "rate limit เก็บตัวนับไว้ที่ไหน ถ้ามีเซิร์ฟเวอร์หลายตัวจะยังทำงานไหม"

**ตอบ:** เก็บในหน่วยความจำของ process เดียว ตอนนี้รันเซิร์ฟเวอร์ตัวเดียวจึงทำงานถูกต้อง
**แต่ถ้าขยายเป็นหลายตัวจะเพี้ยนทันที** เพราะแต่ละตัวนับแยกกัน
ผู้โจมตีที่ยิงกระจายไปหลายเครื่องจะได้โควต้าคูณจำนวนเซิร์ฟเวอร์

**ทางแก้:** ย้ายตัวนับไปเก็บที่ Redis ซึ่งระบบมีการเชื่อมต่ออยู่แล้ว (ใช้เป็น cache)
ระบุไว้ในหัวข้อข้อจำกัดของเอกสาร

### B4. "ทำไม bcrypt cost 10 ไม่ใช่ 12"

**ตอบ:** cost 10 เป็นค่าที่ใช้กันทั่วไปและยอมรับได้ตามคำแนะนำปัจจุบัน
ยิ่ง cost สูงยิ่งปลอดภัยแต่ใช้เวลาคำนวณนานขึ้นแบบทวีคูณ

**จุดที่ต้องระวังในระบบนี้:** เราใช้ bcrypt กับรหัส OTP ด้วย ซึ่งถูกเรียกทุกครั้ง
ที่ขอรหัส ถ้าตั้ง cost สูงเกินจะทำให้ตอบช้าและกลายเป็นช่องให้โจมตีแบบทำให้ระบบล่ม

**ยอมรับ:** ถ้าเน้นความปลอดภัยของรหัสผ่านสูงสุดควรขึ้นเป็น 12
และแยกค่าที่ใช้กับ OTP ออกจากรหัสผ่าน

### B5. "ทำไมเก็บเงินเป็นจำนวนเต็ม ทำไมไม่ใช้ NUMERIC ของ PostgreSQL"

คำถามนี้ลึกและถามคนที่รู้จริงเท่านั้น

**ตอบ:** `NUMERIC` ใช้ได้และแม่นยำเหมือนกัน แต่เลือกจำนวนเต็มหน่วยสตางค์เพราะ

1. เงินบาทไม่มีหน่วยย่อยกว่าสตางค์ จึงไม่ต้องการทศนิยมเลย
2. บวกลบจำนวนเต็มเร็วกว่า และไม่มีปัญหาการแปลงชนิดข้อมูลระหว่างฐานข้อมูลกับ
   JavaScript ซึ่ง `NUMERIC` จะถูกส่งมาเป็นข้อความ ต้องแปลงเองทุกครั้ง
3. ทดสอบง่าย — เทียบค่าตรงๆ ได้โดยไม่ต้องกำหนดความคลาดเคลื่อนที่ยอมรับได้

**ข้อจำกัดที่ยอมรับ:** `Int` ของ PostgreSQL เก็บได้สูงสุด 2,147,483,647 สตางค์
= ประมาณ 21 ล้านบาท จึงกำหนดเพดานระบบไว้ที่ 20 ล้านบาท
ถ้าจะรองรับยอดสูงกว่านี้ต้องเปลี่ยนเป็น `BigInt`

### B6. "ช่องโหว่จับเวลา (timing) เจอได้ยังไง แล้วมั่นใจได้ยังไงว่าไม่มีที่อื่นอีก"

เรื่องนี้เล่าได้ดีที่สุด เพราะเป็นบั๊กที่หายาก

**เล่าลำดับ:** ระบบขอรหัส OTP ถูกออกแบบให้ตอบ**ข้อความเหมือนกันทุกกรณี**
ไม่ว่าอีเมลนั้นจะมีบัญชีหรือไม่ เพื่อไม่ให้ใครไล่เช็กว่าใครสมัครไว้บ้าง
และเขียนข้อทดสอบยืนยันว่าตอบเหมือนกันเป๊ะ — **ผ่าน**

แต่พอตั้งค่าส่งอีเมลจริงแล้ววัดเวลา พบว่า

| อีเมล | เวลาตอบ |
|---|---|
| ไม่มีในระบบ | 0.16 วินาที |
| มีบัญชีจริง | 120.78 วินาที |

ต่างกัน 750 เท่า เพราะโค้ดรอให้ส่งอีเมลเสร็จก่อนตอบ **ใครจับเวลาก็รู้ทันที**
ว่าอีเมลไหนมีบัญชี การป้องกันที่ตั้งใจทำจึงเป็นโมฆะ

**บทเรียน:** ข้อมูลรั่วได้ผ่าน "เวลา" ไม่ใช่แค่ "เนื้อหา" —
เทสที่ตรวจแค่สิ่งที่ตอบกลับมาจับกรณีแบบนี้ไม่ได้เลย

**ตอบส่วน "มั่นใจได้ยังไงว่าไม่มีที่อื่น":** **ไม่มั่นใจ 100%**
ตอนนี้เพิ่มข้อวัดเวลาไว้เฉพาะจุดที่รู้ว่าเสี่ยง (ขอรหัส OTP)
จุดอื่นที่ควรตรวจเพิ่มคือหน้าล็อกอิน ซึ่งใช้ bcrypt เปรียบเทียบที่ใช้เวลาเท่ากัน
ไม่ว่ารหัสถูกหรือผิดอยู่แล้ว จึงเสี่ยงน้อยกว่า

### B7. "ถ้าฐานข้อมูลรั่ว ข้อมูลการเงินของผู้ใช้จะเป็นยังไง"

**ตอบตามจริง:**

| ข้อมูล | สถานะถ้าฐานข้อมูลรั่ว |
|---|---|
| รหัสผ่าน | ปลอดภัย — เข้ารหัสด้วย bcrypt ถอดกลับไม่ได้ |
| รหัส OTP | ปลอดภัย — เข้ารหัสด้วย bcrypt เช่นกัน |
| **รายรับ-รายจ่าย ยอดเงิน เป้าหมาย** | **อ่านได้ทั้งหมด** ไม่ได้เข้ารหัสระดับแอป |
| บทสนทนากับ AI | อ่านได้ |

**อย่าอ้างว่าปลอดภัย** — ให้ตอบว่าพึ่งการเข้ารหัสระดับโครงสร้างพื้นฐานของผู้ให้บริการ
ฐานข้อมูล (เข้ารหัสขณะจัดเก็บ) และการควบคุมสิทธิ์เข้าถึง
แต่**ไม่ได้เข้ารหัสรายฟิลด์ในระดับแอปพลิเคชัน**

**ทางแก้ถ้าต้องการจริง:** เข้ารหัสฟิลด์ที่อ่อนไหวด้วยกุญแจที่เก็บแยกจากฐานข้อมูล
แต่จะทำให้ค้นหาและรวมยอดทำไม่ได้ ต้องแลกกัน

## หมวด C — คำถามเรื่องความน่าเชื่อถือ

### C1. "ความแม่นยำการอ่านสลิป 100% — ทดสอบจากสลิปจริงกี่ใบ"

**นี่คือจุดอ่อนที่สุดของงาน ต้องเตรียมตอบให้ดี**

**ตอบตามจริง:** ชุดทดสอบใช้**ข้อความ OCR ตัวอย่าง 10 รูปแบบ ไม่ใช่สลิปจริง 10 ใบ**
ทุกรูปแบบมาจากบั๊กจริงที่ผู้ใช้แจ้งเข้ามาระหว่างพัฒนา เช่น สลิป ttb ที่อ่านไม่ออก
และสลิปเป๋าตังที่ระบบหยิบยอดเต็ม 60 บาทแทนยอดที่ผู้ใช้จ่ายจริง 24 บาท

ดังนั้นตัวเลข 100% หมายถึง **"ไม่มีบั๊กเดิมย้อนกลับมา"** ไม่ใช่
"อ่านสลิปทุกใบในโลกได้ถูก" — ในเอกสารระบุข้อจำกัดนี้ไว้แล้ว

**ถ้าถามต่อว่าควรทำยังไง:** เก็บสลิปจริงจากหลายธนาคาร 50 ใบ เฉลยยอดไว้
แล้ววัดเป็นเปอร์เซ็นต์ จะได้ตัวเลขที่อ้างอิงได้กว้างขึ้น

### C2. "AI ตอบไม่เหมือนเดิมทุกครั้ง จะทดสอบให้เชื่อถือได้ยังไง"

**ตอบ:** ไม่ทดสอบว่า "ตอบด้วยถ้อยคำอะไร" เพราะวัดไม่ได้ แต่ทดสอบ 2 อย่างที่ตรวจสอบได้แน่นอน

1. **ตัวเลขที่อ้างตรงกับฐานข้อมูลไหม** — ป้อนข้อมูลที่รู้คำตอบล่วงหน้า
   (รายจ่ายรวม 15,319 บาท) แล้วดูว่า AI ตอบเลขนี้ไหม
2. **การกระทำที่บอกว่าทำแล้ว เกิดขึ้นจริงไหม** — ถ้า AI บอกว่า
   "ตั้งเป้าหมายให้แล้ว" ต้องมีเป้าหมายอยู่ในฐานข้อมูลจริง

**เล่าต่อได้ว่าข้อ 2 จับบั๊กจริงได้** — AI ตอบว่า *"พี่เงินช่วยตั้งไว้ในระบบเรียบร้อยแล้ว"*
พร้อมอธิบายแผนออมละเอียด แต่ไม่มีเป้าหมายนั้นอยู่จริง

**บทเรียนที่ตอบได้ดี:** ไล่ตัดสมมติฐานทีละข้อจนพบว่าโมเดลไม่เรียกเครื่องมือที่ให้ไว้เลย
ทั้งที่คำสั่งระบุชัดเจน จึงเปลี่ยนไปเขียนกฎตรวจจับเจตนาในโค้ดแล้วสร้างเป้าหมายเอง
สรุปเป็นหลักการว่า **"เมื่อความถูกต้องของการกระทำสำคัญ อย่าฝากไว้กับการตัดสินใจของโมเดลภาษา"**

### C3. "Prophet ที่ใช้พยากรณ์ แม่นแค่ไหน"

**ตอบตามจริง: ยังไม่ได้วัด** — ระบุไว้เป็นข้อจำกัดในเอกสารแล้ว

**อธิบายวิธีที่ควรวัด:** ทำ backtesting คือเอาข้อมูล 6 เดือนแรกมาเทรน
แล้วให้ทำนายเดือนที่ 7 เทียบกับค่าจริง วัดด้วย MAPE (ค่าความคลาดเคลื่อนเฉลี่ยเป็นเปอร์เซ็นต์)

**เหตุผลที่ยังไม่ทำ:** ต้องมีข้อมูลจริงย้อนหลังหลายเดือนจากผู้ใช้จริง
ซึ่งระบบเพิ่งเปิดใช้ ยังไม่มีข้อมูลมากพอ

### C4. "ถ้าผู้ให้บริการ AI ล่ม ระบบทำอะไร"

**ตอบ:** มีระบบสำรอง 2 ชั้น — เรียกผู้ให้บริการเรียงตามลำดับ
(Typhoon → Groq → OpenAI) ถ้าล้มทุกรายจะใช้**คำตอบสำเร็จรูป**ที่เขียนไว้ล่วงหน้าแทน

**จุดที่น่าสนใจ:** โหมดคำตอบสำเร็จรูปอันตรายกว่าที่คิด เพราะผู้ใช้จะได้คำตอบกว้างๆ
ที่**ดูเหมือนใช้ได้แต่ไม่อิงข้อมูลจริง** และเรียกใช้เครื่องมือไม่ได้
จึงเพิ่มข้อทดสอบตรวจจับสถานะนี้โดยเฉพาะ เพราะพบว่าเกิดขึ้นจริงเป็นครั้งคราวบน production

**ข้อเสนอแนะที่ระบุไว้:** ควรแจ้งผู้ใช้ให้รู้เมื่ออยู่ในโหมดนี้ แทนที่จะตอบเหมือนปกติ

## หมวด D — คำถามเรื่องกระบวนการ

### D1. "ถ้าเพื่อนในทีมแก้โค้ดแล้วทำพัง จะรู้ได้ยังไง"

**ตอบ:** ผูกชุดทดสอบเข้ากับ GitHub Actions แบ่ง 2 ระดับ

| ระดับ | เมื่อไหร่ | ทดสอบอะไร |
|---|---|---|
| 1 | ทุกครั้งที่ส่งโค้ด | ตรวจในเครื่อง 29 ข้อ (~1 นาที) ไม่แตะ production |
| 2 | ทุกวัน 08:00 น. | ยิง production จริงทั้ง 2 ชุด |

ถ้าระดับ 2 ไม่ผ่าน จะแจ้งเตือนเข้า Telegram ทันที

**เหตุผลที่ไม่รันชุดเต็มทุกครั้งที่ส่งโค้ด:** เพราะสร้างบัญชีทดสอบจริง
และกินโควต้าจำกัดอัตราที่ผู้ใช้จริงต้องใช้

### D2. "ทำไมชุดทดสอบต้องเรียงลำดับด้วย"

ถ้าถามมาแสดงว่าอ่านโค้ดจริง

**ตอบ:** ชุดความปลอดภัยมีข้อทดสอบที่**ยิงล็อกอินผิดรัว 25 ครั้ง**
เพื่อพิสูจน์ว่าระบบจำกัดอัตราทำงาน ซึ่งจะกินโควต้าจนชุดที่รันทีหลัง
สมัครบัญชีทดสอบไม่ได้ จึงต้องรันชุดความน่าเชื่อถือก่อนเสมอ
และในชุดความปลอดภัยเองก็ย้ายขั้นเก็บกวาดขึ้นมาก่อนข้อทดสอบนั้น

## หมวด E — ถ้าตอบไม่ได้ ทำยังไง

**ห้ามเดา** กรรมการจับได้ทันทีและเสียความน่าเชื่อถือทั้งงาน

**สูตรตอบ 3 ขั้น**

1. ยอมรับตรงๆ — *"ข้อนี้ผมยังไม่ได้ตรวจครับ"*
2. บอกสิ่งที่รู้ที่ใกล้เคียง — *"แต่ในระบบมี... ซึ่งเกี่ยวข้องกันตรงที่..."*
3. บอกวิธีที่จะหาคำตอบ — *"ถ้าจะตอบให้แน่ชัดต้องทดลอง... แล้วดูว่า..."*

ขั้นที่ 3 สำคัญที่สุด เพราะแสดงว่ารู้วิธีหาคำตอบ ซึ่งเป็นสิ่งที่วัดจริงในระดับปริญญาตรี

## สรุปจุดอ่อนที่ต้องรู้ตัวไว้

เรียงตามโอกาสที่จะถูกถาม

| # | จุดอ่อน | ท่าทีที่ควรใช้ |
|---|---|---|
| 1 | ความแม่นยำสลิปวัดจากตัวอย่างสังเคราะห์ ไม่ใช่สลิปจริง 50 ใบ | ยอมรับ + บอกวิธีที่ควรทำ |
| 2 | ยังไม่ได้วัดความแม่นยำการพยากรณ์ (Prophet) | ยอมรับ + อธิบายวิธี backtesting |
| 3 | JWT บนเว็บเก็บใน localStorage | ยอมรับ + อธิบายสิ่งที่ลดความเสี่ยง |
| 4 | เพิกถอน token ก่อนหมดอายุไม่ได้ | ยอมรับ + เสนอ refresh token |
| 5 | ตัวนับจำกัดอัตราอยู่ในหน่วยความจำ ขยายหลายเซิร์ฟเวอร์ไม่ได้ | ยอมรับ + เสนอย้ายไป Redis |
| 6 | ข้อมูลการเงินไม่ได้เข้ารหัสระดับแอป | ยอมรับ + อธิบายว่าพึ่งการเข้ารหัสของผู้ให้บริการฐานข้อมูล |
| 7 | ไม่มี code coverage | อธิบายว่าเป็น black-box จึงวัดเป็น behavior coverage |
| 8 | ไม่ได้รันเครื่องมือสแกนอัตโนมัติ | อธิบายว่าเครื่องมือจับ Broken Access Control ไม่ได้ |

**ทั้ง 8 ข้อนี้ระบุอยู่ในเอกสารแล้ว** — ตอบได้ว่า *"ข้อนี้เราระบุไว้ในหัวข้อข้อจำกัดครับ"*
ซึ่งแสดงว่ารู้ตัวตั้งแต่แรก ไม่ใช่เพิ่งมารู้ตอนถูกถาม
